AI 短劇 Skill 開源研究 · 2026.10

九個開源 Skill，
拆成可以抄的寫法／

我們把 eli5、AI 寫作、AI 短劇三類各挑三個真實 repo 拉下來逐檔讀過。這份筆記只記能直接搬進我們短劇 Skill 的寫法：指令怎麼寫得短、流程怎麼拆、檢查怎麼落地、references/ 與 templates 怎麼分工。

01

SKILL.md 只放「流程與邊界」

mblode 的 eli5 本體只有 42 行，shuohao 的劇本 Skill 159 行。知識、詞表、格式細節搬到 references/，並寫明什麼訊號出現才讀哪一份。

02

品質檢查要能被執行

從「交稿前自檢清單」到「腳本質量門」是一條光譜。短劇最好的兩個 repo 都把時長、台詞長度、鉤子位置交給腳本檢查，模型只負責寫戲。

03

先定義讀者與不做的事

每個好 Skill 都有一段「IS NOT／邊界」，把相鄰工作指給別的 Skill。這比加長規則更能讓輸出穩定。

R1
卷一 · 輸出風格控制、精簡指令

eli5：同一個名字，三種完全不同的寫法

三個都叫 eli5，篇幅從 42 行到 116 行。差異不在長短，而在它們如何定義「讀者」與「交出什麼」。

dzhng/skills · eli5

72 行單一 SKILL.mdMIT更新 2026-10-05

把技術規格講給「懂技術、但沒看過這份程式碼」的人聽。最精準的一份讀者定義。

skills/engineering/eli5/
└── SKILL.md
    ├ frontmatter
    │   disable-model-invocation: true
    ├ ## The Register   ← 語域定義
    ├ ## Workflow       ← 4 步
    ├ ## Output         ← 固定 3 個標題
    └ ## Rules
  1. 1
    一句話定調，「簡化講法，不簡化主張」

    開頭就把風格寫成可檢驗的原則，後面所有規則都從這句長出來。

    Plain language, full precision: simplify the telling, never the claims.
  2. 2
    把風格寫成可被其他 Skill 引用的「語域」

    The Register 一段寫明「別的 Skill 要輸出給沒參與工作的人看時，指到這裡」。風格是一個共用模組，不是每個 Skill 各寫一次。

  3. 3
    失敗判準寫成一句測試

    「讀者還得問『這段再解釋一下』就算失敗」。比列十條形容詞更好執行。

  4. 4
    何時換表達形式，給出可觀察的訊號

    文字裡出現 only when、before、unless 而讀者仍說不出第二次呼叫會怎樣，就改用偽代碼。

  5. 5
    輸出固定成三個標題加一句收尾

    Problem → Solution → Schema changes，最後一句說使用者會注意到什麼。沒有變更也要明說「沒有」。

可借鏡

為短劇寫一段「讀者是誰」：例如分鏡的讀者是視頻模型，它沒看過劇本，所以每鏡要自包含。

要注意

disable-model-invocation 讓它只能手動呼叫，適合工具型 Skill；短劇主流程反而需要自動觸發。

mblode/agent-skills · eli5

42 行 + 99 行 reference7 條 evalsMIT更新 2026-10-06

最短也最有紀律的一份。用一張「形式階梯」表決定輸出是文字、圖、網頁還是影片。

skills/eli5/
├── SKILL.md          42 行：風格 + 選形式
├── references/
│   └── formats.md    STE100、圖、HTML、影片
└── evals/
    └── evals.json    7 個情境 + assertions
  1. 1
    開頭先寫 IS NOT

    第一行就說「產品文案找 ghostwriter、投影片找 presentation-creator」。邊界先於規則。

  2. 2
    選項表帶「成本」欄，規定取最低一階

    文字 → 受控英文 → 圖 → HTML → 影片，每階寫明何時用、成本多高；「自己選時，沒問過就不超過圖」。

  3. 3
    漸進載入寫成條件句

    「除了純文字以外的形式，先讀 references/formats.md」。本體保持 42 行，細節按需讀。

  4. 4
    明確禁止儀式性輸出
    Return the explanation itself. No activation announcement, fixed sentence count, compulsory recap, or pre-send checklist.
  5. 5
    共用詞表只放一份

    AI 腔詞表指向兄弟 Skill ghostwriter/references/tells.md，「整個集合唯一的一份」，避免多處維護。

  6. 6
    evals 跟 Skill 放一起，但寫明「解釋時不要載入」

    每條 eval 是 prompt + expected + assertions，例如「保留 git rebase --onto main 原文」「每句不超過 25 字」。

可借鏡

形式階梯可以直接改成短劇的「產出層級」：大綱 → 劇本 → 分鏡 → 提示詞，使用者沒點名就停在最低必要層。

要注意

它依賴同一 repo 的兄弟 Skill。單獨拷走時，引用的 tells.md 會斷掉。

DreambigOu/ELI5

116 行附評測部落格MIT

按聽眾調整說法：年齡、年級、職位、家人。最典型的「查表式」風格控制。

skills/eli5/
└── SKILL.md
    ├ description  ← 塞滿觸發語
    ├ Step 1 辨識聽眾   4 張表
    ├ Step 2 讀素材
    ├ Step 3 寫解釋     結構 + 語言校準
    ├ Examples          3 組
    └ Important Reminders
  1. 1
    description 列出口語觸發詞，連部分匹配都寫

    「explain to my wife」「tell my boss」也要觸發。對中文使用者，這裡就該寫「白話一點」「講給我媽聽」。

  2. 2
    聽眾 × 風格對照表

    每列寫「他們在乎什麼／用什麼框架講」。把模糊的「看對象調整」變成查表。

  3. 3
    固定的四段結構

    是什麼 → 類比 → 按需加細節 → 對你有什麼影響。

  4. 4
    預設值寫死

    沒說聽眾就當 5 歲。每個分岔都有預設，模型不用停下來問。

可借鏡

「題材 × 觀看契約」可以照這個表格做：甜寵、復仇、懸疑各自在乎什麼爽點、用什麼節奏。

要注意

「80% 正確也比聽不懂好」跟 dzhng 的「不簡化主張」正好相反；放進短劇裡等於允許改劇情。還有「You are an expert」式人設對輸出幾乎沒有約束力。

卷一帶走的寫法

  1. 一句可檢驗的原則先行，其餘規則從它推出。
  2. 邊界寫在最前面：IS NOT 加上「這種事交給哪個 Skill」。
  3. 選項用表格，欄位要有「何時用」與「代價」，並規定預設取哪一格。
  4. 禁止儀式性輸出：不宣告模式、不強制總結、不附自檢清單給使用者看。
  5. evals 放在 Skill 旁邊，但寫明執行任務時不要讀它。

卷二 · 流程拆解、品質檢查清單、避免 AI 腔

AI 寫作：先說清楚 AI 腔從哪來，再給改法

兩個去 AI 腔的 Skill 都源自維基百科 WikiProject AI Cleanup 的〈Signs of AI writing〉，但組織方式不同；第三個是 Anthropic 官方的協作寫文件流程。

blader/humanizer

397 行v3.1.026 個模式MIT

去 AI 腔最成熟的一份。重點不是詞表，而是「為什麼」與「強度分級」。

humanizer/
├── SKILL.md
│   ├ 為什麼 AI 文字會這樣（6 類）
│   ├ How to work  4 步
│   ├ Voice / What to return
│   ├ A–F 26 個模式（強→弱）
│   └ When not to act
├── scripts/validate-package.py
├── .github/ISSUE_TEMPLATE/new-pattern.yml
└── CHANGELOG.md
  1. 1
    先解釋成因，模式才有判斷依據

    「模型挑最適合最多讀者的預設選擇；人為一個讀者挑，所以不均勻且具體。」六大類（鋪陳、規律節奏、膨脹、格式、殘留、寫錯讀者）都是這個成因的變形。

  2. 2
    模式按強度排序並標「單獨不算」

    §1–§5 看到一次就改；標 weak alone 的要和其他痕跡同時出現才動手。避免過度修改。

  3. 3
    每個模式同一個格式

    Watch for → Problem → Before → After。前後對照讓模型學到改法，而不只是禁詞。

  4. 4
    四步流程裡有「改完再掃一次最常存活的痕跡」

    標記 → 起草 → 檢查（有沒有增刪事實、數字、引語）→ 定稿；並點名改寫後最常殘留的 §1、§2、§6、§8、§19。

  5. 5
    三種交付模式

    貼上的文字回傳草稿 + 殘留清單 + 定稿；指定檔案只寫定稿；被其他任務嵌入時只回定稿。

  6. 6
    「何時不要動手」與「保留作者聲音」

    引語、標題、專名不改；有寫作樣本時樣本優先，連破折號規則都讓位。

可借鏡

短劇台詞的 AI 腔（說教、總結式台詞、每句都押排比）可以照「成因 → 分級模式 → 前後對照」寫一份 references/。

要注意

詞彙層的例子全是英文。中文 AI 腔要自己整理，不能直接翻譯。

jpeggdev/humanize-writing

464 行 + 278 行 reference8 道 passMIT

同一個來源，改寫成依序執行的八道 pass，並把詞表移到 references。

humanize-writing/
├── SKILL.md
│   ├ Core Philosophy（pattern stacking）
│   ├ Pass 1 結構 … Pass 8 加人味
│   ├ Read It Out Loud 測試
│   ├ What to Preserve
│   └ Output Format（Changes 表）
└── references/
    └── ai-tells.md   Tier 1 / Tier 2 詞表
  1. 1
    pass 的順序就是優先序

    先拆結構（每段都收一個金句、清單永遠三項），再處理誇大、詞彙、語法、節奏。最明顯的先修。

  2. 2
    詞表分級並附「人類替代詞」

    Tier 1 看到就改，Tier 2 出現三個以上才算訊號；每個詞旁邊都有替代寫法，或直接寫「刪掉」。

  3. 3
    疊加原則

    同一處同時中了粗體、引號、破折號，算一個強訊號而不是三個，避免灌水。

  4. 4
    修改紀錄表有行數上限

    Changes 表只列有改的 pass，超過 8 行代表「改太多或解釋太多」。

  5. 5
    審查模式要求真的去數

    「實際數破折號再下結論」「三列表格可能真的只有三件事」。檢查清單裡寫了反例。

可借鏡

把「改稿紀錄最多 N 行」「先數再說」直接寫進我們的審查規則。

要注意

Pass 8「加人味」鼓勵加入第一人稱細節；用在改編劇本時會變成憑空加戲，要關掉。

anthropics/skills · doc-coauthoring

375 行3 個階段官方範例

流程拆解的教科書：每個階段寫目標，每節寫步驟，最後用「沒有上下文的讀者」驗收。

skills/doc-coauthoring/
└── SKILL.md
    ├ When to Offer（觸發與邀請語）
    ├ Stage 1 Context Gathering
    ├ Stage 2 Refinement & Structure
    │   Step 1 澄清 → 2 發想 5–20 個
    │   → 3 篩選 → 4 缺口 → 5 起草
    │   → 6 精修（只做局部替換）
    ├ Stage 3 Reader Testing
    └ Final Review
  1. 1
    每個階段先寫一行 Goal

    「縮小使用者知道的和 Claude 知道的之間的落差」。模型迷路時回到這行。

  2. 2
    從未知最多的段落開始

    決策文件先寫提案、規格先寫技術方案，摘要最後寫。

  3. 3
    發想與篩選分開

    先列 5–20 個選項讓使用者勾，再起草。避免第一版就定型。

  4. 4
    收斂訊號寫成數字

    連續三輪沒有實質修改，就問「有什麼可以刪掉」。

  5. 5
    用新的子代理當讀者測試

    預測 5–10 個讀者會問的問題，交給只拿到文件的子代理回答，答錯的地方就是缺口。

可借鏡

「冷讀者測試」很適合分鏡：把單鏡提示詞丟給沒看過劇本的子代理，問「這鏡誰在說話、在哪、手上拿什麼」。

要注意

它高度依賴來回對話。短劇多集量產時，應改成批次跑完再回報，只在真正的創作分岔才問。

卷二帶走的寫法

  1. 品質規則先寫成因，再列模式；模式附強度與「單獨不算」。
  2. 每條規則用同一格式：觀察點、問題、改前、改後。
  3. 流程最後一步是「再掃最容易殘留的那幾項」，不是泛泛的「檢查一遍」。
  4. 明寫「不能新增事實」；改編類任務尤其要擋住模型加戲。
  5. 驗收用沒有上下文的讀者（子代理），而不是寫的人自己。

卷三 · 多階段工作流、結構化輸出、references 與 templates 分工

AI 短劇：兩種成熟路線，一個產品內建版本

shuohao 走「JSON + 腳本質量門」，zenstory 走「Markdown 單一真相 + 規則分級 + 獨立審查」。mediago 則是把 Skill 綁在 App 的文件類型上。

eternityspring/shuohao-skills

6 個 SkillNode 零依賴10–18 道腳本質量門Apache-2.0更新 2026-09-26

小說 → 大綱 → 角色 / 美術 → 劇本 → 分鏡，每一段都是獨立可拷走的 Skill，用 JSON 接力。GitHub 上有大量 fork。

skills/novel-script/
├── SKILL.md          159 行：Step 0–4
├── references/
│   ├── script-pass.md   怎麼寫一集
│   ├── schema.md        JSON 欄位
│   ├── report-style.md
│   └── test-fixtures/upstream/
├── scripts/
│   ├── novel-script.mjs seed / validate / render
│   └── selftest.mjs     154 項斷言
├── examples/渡口-script.json
└── assets/report.webp
  1. 1
    一句分層原則管住整條管線
    剧本管戏，分镜管拍

    台詞要反覆推翻，綁上鏡頭每改一句都要重排，所以劇本層不准有鏡號。每個 Skill 都有一段「邊界（不做的事）」。

  2. 2
    確定性的事實交給腳本搬，不讓模型重想

    seed 從 outline.json 搬目標秒數、鉤子、懸念、爽點；「这些事实不要让模型重新想一遍」。模型只填 scenes。

  3. 3
    校驗是不能跳的一步，而且是程式

    每集時長 ±15%（台詞 4.5 字/秒、動作 2.5 秒/拍）、單句 ≤ 35 字、鉤子落在前 3 拍、每場至少一個動作拍。有違規就逐條修、重跑到通過。

  4. 4
    *-pass.md 分三層：硬規則、修改紀律、手感規則

    硬規則有門；手感規則「不設門，但決定戲好不好看」；最後一張「常見病 → 症狀 → 治法」表（廣播劇、文學病、開場死畫面、注水…）。

  5. 5
    為 AI 視頻寫的「常見動作」判據

    上船、坐下、遞東西放心寫；用工具擋物、睫毛顫、以寸計位移要改寫。附 ✗/✓ 對照表。

  6. 6
    質量門失敗會累積成統計

    每次 validate 追加到 .gates.jsonl，stats 回答：哪道門最常響（該改的是措辭）、哪道從沒響過（死門或已內化）。用數據改 Skill 文字。

  7. 7
    範例同時是品質基準與測試夾具

    《渡口》6 集完整樣例對上游全部門通過；selftest 每道門都有擊穿用例。

可借鏡

seed / validate / render 三個子命令、每批 ≤ 3 集、.gates.jsonl 回饋迴圈。這是目前看到最工程化的短劇 Skill。

要注意

台詞存 JSON 對編劇不友善，要靠 render 出 Markdown 與 HTML 報告補回可讀性；維護成本也最高。

zenstory-ai/drama-skills

11 個 SkillPython附評測語料MIT更新 2026-10-03

一個路由 Skill 加十個階段 Skill，每集只維護五份 Markdown。規則有編號、有分級，審查由另一個 Skill 獨立做。

skills/
├── short-drama/        路由 + Dashboard
├── short-drama-write/
│   ├── SKILL.md        104 行
│   ├── references/
│   │   ├── stage-contract.md  SCR-01…22
│   │   ├── script-craft.md
│   │   ├── dialogue-craft.md
│   │   └── screenplay-format.md
│   ├── assets/       ← templates
│   │   ├── screenplay.md
│   │   └── episode-card.json
│   └── scripts/duration_estimate.py
├── short-drama-review/
└── …（develop / assets / storyboard /
    video-prompts / produce / edit）
evaluations/  16 個題材案例 + rubric + judge
  1. 1
    路由表把「誰負責什麼」寫成一張表

    使用者要做什麼 → 哪個 owner Skill → 產出哪份檔。明確的單階段請求直接交給子 Skill，跨階段才經過路由。

  2. 2
    不建立平行的結構化真相

    每集只有 剧本.md、视觉设定.md、分镜.md、图片提示词.md、视频提示词.md；「不要為補齊名義流水線偽造上游」。

  3. 3
    「按需知識」：訊號 → 讀哪份 reference

    輸入有核心選擇、精確倒計時、關鍵物證時才讀 script-craft.md 對應小節；預設只讀 SKILL.md 和直接輸入。

  4. 4
    規則有 ID 與四級分類

    structural_invariant（阻斷）→ reviewed_invariant（需證據判斷）→ craft_default（可覆蓋）→ taste_option（創作者選擇，不算缺陷）。審查意見引用規則 ID。

  5. 5
    寫與審拆成兩個 Skill

    審查「優先由未參與當前版本創作的 reviewer 執行」，只寫問題、證據、影響與修訂要求，不替 owner 改檔。

  6. 6
    不可逆動作要先預覽再確認

    實際生成媒體走 produce：先預覽，再顯式確認，最後執行。

  7. 7
    只在真實創作分岔才問
    不要拿 schema、目录、事务或检查器询问创作者。

可借鏡

規則 ID + 四級分類、訊號觸發式 references、寫審分離、題材案例評測集。對編劇最友善的一套。

要注意

卷三帶走的寫法

  1. 一句分層原則（劇本管戲、分鏡管拍）比十條規則更能守住階段邊界。
  2. 能算的交給腳本：時長、字數、鉤子位置、每段秒數。模型只做創作判斷。
  3. references/ 放「怎麼寫」，templates/（兩個 repo 都叫 assets/）放「寫成什麼樣」的空白骨架，examples/ 放填好的完整樣例。
  4. 規則加 ID 與等級，審查才能引用、才能區分「錯誤」與「品味」。
  5. 跟視頻模型綁定的規則（秒數上限、動作寫法、提示詞語言）獨立成按模型區分的檔案。

套到我們的短劇 Skill：建議骨架

short-drama-skill/
├── SKILL.md            ≤ 200 行
│   ├ description：中文觸發語
│   ├ 一句分層原則 + 不做的事
│   ├ Step 0 定範圍 → 4 交付
│   └ 訊號 → 讀哪份 reference
├── references/        給模型讀：怎麼寫
│   ├── script-pass.md
│   ├── storyboard-pass.md
│   ├── rules.md        ID + 四級分類
│   ├── anti-ai-tone.md 中文台詞 AI 腔
│   └── models/seedance.md
├── templates/         給模型填：長什麼樣
│   ├── 剧本.md
│   └── 分镜.md
├── examples/          一集完整樣例
├── scripts/validate.py 時長、字數、鉤子
└── evals/evals.json    題材案例 + 斷言
  1. 開頭寫一句分層原則與「不做的事」例如「劇本管戲，分鏡管拍」，接著列出這個 Skill 不碰的工作與該交給誰。（shuohao、mblode）
  2. description 寫使用者真的會說的中文「幫我寫一集」「改成短劇」「拆分鏡」「去 AI 味」，包含部分匹配。（DreambigOu、shuohao 的 triggers）
  3. SKILL.md 寫流程，references 寫知識，並寫明讀取訊號「輸入有精確倒計時才讀 script-craft.md §6.3」。（zenstory、mblode）
  4. templates 只放空白骨架，examples 放填好的樣例骨架決定格式，樣例示範品質，兩者都不寫規則。
  5. 能算的寫成腳本，Step 標「不能跳」每集時長、單句台詞字數、鉤子在前 3 拍、每段 ≤ 15 秒。（shuohao、mediago）
  6. 規則編號並分四級阻斷、需判斷、預設可覆蓋、品味。審查只引用編號。（zenstory）
  7. 去 AI 腔規則先寫成因、再寫分級模式與前後對照中文台詞自己整理：說教、總結式金句、排比、每句都解釋情緒。（humanizer、humanize-writing）
  8. 寫與審分開，審查用沒看過上下文的讀者分鏡丟給子代理問「誰、在哪、拿著什麼」。（zenstory、doc-coauthoring）
  9. 跟視頻模型綁定的規則獨立成檔15 秒上限、動作寫法、提示詞語言因模型而異。（mediago 與 shuohao 的衝突）
  10. 預設值寫死，只在真實創作分岔才問沒說集長就用 2 分鐘、沒說批次就每批 3 集，自動續跑。（DreambigOu、zenstory、shuohao）

references/

模型寫之前要知道的事：硬規則、手藝、常見病、按模型區分的方言。可以很長，但按訊號載入。

templates/

輸出的空白形狀：標題層級、場景標頭、對白格式、欄位順序。不含規則說明。

examples/

一集通過全部檢查的完整成品，同時當品質基準與測試夾具。
